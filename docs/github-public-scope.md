# Import public GitHub repository scope

In an undeployed vendor workspace, open **Reports** and enter a repository URL under **Import a public repository as scope**. Click **Look up public repository**, or press Enter in that input. Review its repository name and archived status, then choose **Use repository as primary scope**. This replaces only the editable primary scope. Existing program name, other scopes, reward policy and time windows stay intact. Normal encrypted draft autosave/file recovery and deployment backup gates apply.

To identify a specific revision, select **Pin scope to the current HEAD commit** before lookup. After public-repository validation, the client requests `/commits/HEAD` with GitHub's [SHA-only media type](https://docs.github.com/en/rest/commits/commits#get-a-commit). It accepts a full 40-character SHA-1 identifier and previews `https://github.com/owner/repository/tree/<sha>`. Applying that URL stores the revision in the existing primary-scope field and therefore in its normal scope digest and encrypted backup. It does not follow future HEAD changes. A failed or invalid SHA response fails the lookup; it never silently falls back to the mutable repository URL.

The SHA response has a 128-byte limit and shares the original 15-second deadline with the metadata request. Commit messages, authors and diffs are not requested. Changing the pin option cancels and invalidates the previous lookup. The repository and HEAD reads are not an atomic snapshot, and the SHA remains GitHub-reported: this feature does not download/recompute the Git object, verify signatures, prove ownership or guarantee long-term object availability.

The import does not contact GitHub until requested. Editing the lookup URL, cancelling, leaving the component or starting another lookup aborts the previous request and discards late results. Enter in the lookup input starts lookup rather than submitting the surrounding deployment form. Lookup input/preview are transient; only the explicitly applied scope URL becomes part of the role vault. It does not change historical deployment snapshots or already deployed policy.

The client uses GitHub's [Get a repository endpoint](https://docs.github.com/en/rest/repos/repos#get-a-repository), which supports public metadata without authentication. It pins API version `2022-11-28`; a read-only September 10 check against `octocat/Hello-World` returned HTTP 200 with the expected public/identity fields. That HTTP probe is separate from the browser tests, which intercept GitHub responses.

Only `https://github.com/owner/repository` URLs are accepted, with an optional trailing slash. Queries, fragments, user information, alternate hosts, extra path segments and encoded paths are rejected before fetching. Requests go to fixed `https://api.github.com/repos/...` paths with no credentials, authorization token, request body or referrer. Browser/network connection metadata remains visible to GitHub. No report content, actor secret, policy prose, source code or release asset is uploaded/downloaded by this feature.

The response must identify the requested repository, its canonical GitHub URL, public visibility and non-disabled status. Archived repositories are identified in the preview. Redirects are refused, so renamed repositories require their current URL. Responses are limited to 256 KiB of received bytes and strict UTF-8 JSON; the complete lookup has a 15-second application deadline. Browser suspension may delay timers. Rate-limit/permission errors leave the draft intact and require explicit retry.

Without the pin option, this imports a mutable public reference. Neither mode proves ownership, authorization to test, contract identity or policy correctness. GitHub App installation/permissions, private repositories, release/patch-reference import, webhooks, and deployment provenance remain separate roadmap work. No GitHub write or native-wallet transaction is performed by the import.
