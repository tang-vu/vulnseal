# Use independent browser roles

Connected restoration holds a fixed copy of the selected identity, saved reports and journal while waiting for Lace. Existing ledger reports must match the saved commitment and ciphertext digest, and their submission receipt must match the contract's hash of the commitment, ciphertext digest and researcher key. Researcher workspaces additionally verify their own derived researcher authority; vendor authority is checked by the role session.

If a saved report has a local finalization claim but is absent from the current ledger, connected restoration refuses the contradiction. Choose **Restore backups without connecting Lace** to retain access to the report and inspect its journal, then investigate the selected network and public evidence before reconnecting. Prepared reports and uncertain attempts without saved finalization may still be absent; their absence does not establish that resubmission is safe. These checks compare backup claims with the configured ledger source. They do not authenticate that source, prove finality, recover deployment addresses or automatically reconcile/retry transactions.

The submission journal retains at most 200 attempts. Its current count is shown in the workspace. At capacity, new contract actions stop before command preparation or wallet/proof work; the final checkpoint also enforces the limit. Existing reports, read-only checks and encrypted export remain available. No old entries are automatically removed, and journal archival/pruning is not implemented; keep the full backup.

Both the unlocked journal and wallet-free inspector show ten attempts per page, in reverse saved-entry order. Search locally by transaction ID, report ID or operation name; private note text is not searched. **Older attempts** and **Newer attempts** navigate the retained history. Filtering does not change the backup or contact public services. Checks for entries leaving the page are closed, and changed journal data returns the display to its newest page.

Wallet setup has a two-minute overall deadline covering connector discovery, authorization status, configuration and shielded-address reads. If it expires, the form becomes available again and ignores late setup results. Lace may still display or complete its own connection prompt; review that prompt before trying again. Setup does not submit a transaction. This deadline does not cover later proof generation, balancing or chain finality.

Before wallet balancing and before submission preparation, authorization is checked again with a separate two-minute deadline. A timed-out check does not proceed when a late response arrives. The later authorization check after the transaction identifier is saved remains inside the existing submission deadline; failures there retain the identifier for reconciliation. These limits do not cancel an already started wallet operation or establish that another attempt is safe.

Wallet balancing itself has a five-minute deadline after authorization succeeds. If it expires, VulnSeal stops waiting and will not decode or submit a late balanced transaction. Lace may still display or complete that request, so review it before starting another attempt. The connector does not expose cancellation for balancing; this timeout does not cover proof generation or chain finality.

Each proving-key, verifier-key or ZKIR download has a two-minute deadline including its response body and a 64 MiB limit measured from received, decompressed bytes. Redirects are rejected. Failed downloads do not supply partial artifacts. These limits do not authenticate the release host or bound the complete proving operation: the SDK may fall back to proof-server key material when a local artifact fetch fails.

The complete browser proof step has a separate ten-minute deadline, including SDK artifact fallback and HTTP retries. On expiry, the action returns an error and a late proof cannot continue to wallet balancing or submission. The proof server may continue working: the SDK exposes no operation-wide cancellation signal. There is no automatic retry. Browser suspension or synchronous work can delay timer delivery, and this deadline does not cover later SDK finality polling.

Saved-report selection shows authenticated private titles alongside full report IDs. **Find saved reports** filters locally by title, affected asset or ID, ignoring case. The selected report remains available even when it falls outside the search; filtering never changes the selection or starts a report action. Duplicate titles remain distinguishable by ID. Titles are decrypted sequentially on this device, never requested from a service, and discarded with the selector when the workspace is closed or locked. Invalid ciphertext is not used as title metadata; its ID remains selectable for inspection. Search state is not added to backup files.

For a saved **Anchor patch** attempt, report reconciliation also compares the attempt's exact private note text against the replayed public patch commitment, including its report binding. Later edits are not substituted for the saved snapshot. A match provides additional comparison evidence; it does not authenticate the backup, verify all transaction arguments or make another submission safe.

Open **Open role workspace** from the demo, or visit `/#roles`. Use a separate browser profile for each participant. The workspace requires a compatible Lace connector and configured Midnight proof/indexer services for transactions; it has no guided transaction mode.

1. **Vendor:** prepare a vendor identity, download its encrypted role backup and enable encrypted browser autosave. Open **Reports**, review program policy fields, and deploy. Save the updated role backup containing the contract address. Download the public program invitation and share it through your agreed channel.
2. **Researcher:** open a fresh role workspace, confirm the invitation's origin/address, and join using Lace. Save the researcher role backup and enable encrypted browser autosave. Use **Prepare report** to encrypt locally and retain its commitment preimage. Wait for the updated browser copy to be saved and retain an updated file. In **Reports**, **Upload saved ciphertext** sends that exact backed-up envelope; failures can be retried after restoring the same backup. **Submit prepared report** also uploads the same ciphertext before starting its contract call, and storage failure stops that call. Multiple prepared reports remain in the vault and selector.
3. **Recipient/vendor:** create a receiving key in **Disclosure exchange** and save its separate receiving-key backup. Share only its public key; confirm the fingerprint independently. The researcher encrypts the selected report for that key. The vendor opens the received disclosure and chooses **Add report to vendor workspace**; this checks the current ledger. Save the updated vendor role backup.
4. **Vendor:** select the report, read its private contents, begin triage and accept/reject with private decision notes. For accepted reports, anchor a patch reference.
5. **Researcher:** refresh ledger, select the same report, perform the retest and submit its result with private notes. Failed retests allow a revised vendor patch; successful retests permit vendor payout authorization. Authorization does not transfer funds. The vendor can close rejected or authorized reports.

To resume, restore the appropriate single-role file and password in a fresh role workspace. Existing-program restores connect Lace, verify authority and check saved reports before installing the session. Prepared reports may be absent from the ledger until submitted. If restoring a vendor backup made before deployment, enter the known contract address under **Reconnect an existing program**; the key must match the owner.

For a storage outage or lost upload response, keep the prepared report and its backup rather than preparing a replacement. Offline file/browser recovery exposes **Upload saved ciphertext** without Lace; it preserves the report ID, key, salt and content address. Either participant holding a saved disclosure can restore its ciphertext this way. Acknowledged storage does not prove long-term availability or ledger submission. See [ADR-0021](adr/0021-prepared-ciphertext-recovery.md).

For device-local persistence, choose **Enable encrypted browser autosave**, enter a non-sensitive label and password, and wait for **Saved encrypted browser copy**. Future role-vault changes are saved automatically. In a fresh tab, select that copy and unlock with its password; deployed programs still undergo the normal Lace/ledger checks. A successful browser save also satisfies the transaction backup gate. Keep downloaded backups because browser data can be cleared or evicted. If another tab changes the same copy, autosave stops instead of overwriting it; reopen the latest copy in a fresh tab or export the current workspace to a separate file. See [ADR-0011](adr/0011-encrypted-browser-autosave.md).

Vendor program fields now live in the encrypted role vault (v11), including unfinished scope/reward text and selected response/disclosure windows. Switching tabs, unlocking the saved browser copy or restoring its file preserves them. Wait for the updated save before deploying. Incomplete drafts can be backed up but must pass normal form validation before deployment. Current releases read older vaults; older releases cannot open v11. A saved draft is not proof of the policy deployed on-chain. See [ADR-0024](adr/0024-vendor-program-drafts.md).

To export or remove a stored copy, stop autosave in the current tab, open **Manage saved browser copies**, and load the catalog. Select the label/revision, then download its existing encrypted envelope; no password or wallet connection is needed to export. Keep the original password and test **Restore one role** in a separate browser profile before relying on the file. To delete, review the selected copy and acknowledge the loss warning. If another tab updated it, reload and review the latest revision first. Deletion affects only that browser row; an old autosave writer cannot recreate it. Deleting the copy used by the open workspace resets its transaction backup gate, so save again before submitting. Other downloaded copies, server ciphertext and on-chain records remain. This is logical deletion, not guaranteed forensic erasure.

Save a new role backup after adding reports/disclosures or learning a deployment address. Confirm each download is retained. Current backups retain incomplete researcher drafts, per-report working notes/tier selections and submission attempts. Version 6 also retains SDK finalization receipts after the encrypted checkpoint succeeds. Receiving keys need a separate backup. Vendor program text is retained when a v11 program draft exists; older backups do not gain missing historical policy text; working notes are editable, not an append-only transition history. If a transaction response is uncertain, reconcile it independently. A missing saved receipt does not prove failure or permit resubmission. If receipt storage fails after finalization, keep the tab open and download the updated backup before leaving. See [ADR-0018](adr/0018-saved-sdk-finalization.md).

Real role submissions require active encrypted browser autosave: each identifier is persisted in the encrypted **Submission journal** before the wallet submission call. A storage failure prevents that call. This also retains the identifier if the connector or later SDK finality response is lost. Restore the browser copy to recover its journal, or export an updated encrypted file through the catalog. Older downloaded files may predate an attempt. A recorded attempt does not prove broadcast or success. Choose **Check transaction status** to match the identifier in the indexer and compare its block against RPC finality. Missing data remains unknown; finalized inclusion displays the indexer's result without authorizing a retry. Observations are timestamped and refreshed on demand, not stored as trusted receipts. Safe semantic retry remains incomplete. See [ADR-0012](adr/0012-submission-journal.md) and [ADR-0013](adr/0013-transaction-observations.md).

After the durable identifier checkpoint, the connector submission response has a two-minute wait limit. If it expires, the operation returns the same unknown-outcome error and retained identifier as a connector failure. Check that identifier in the wallet and public services; expiry does not cancel a wallet broadcast, prove failure or allow retry. Late responses do not become a successful result for that finished call. If the final authorization check itself returns after expiry, the application prevents its callback from starting a new broadcast. Browser suspension can delay timers. This limit does not cover initial wallet connection, balancing/proving, checkpoint storage or subsequent SDK finality polling.

The role workflow is implemented, with native Lace multi-profile transaction validation still outstanding. See [validation-report.md](validation-report.md) for the distinction between live browser file/crypto checks, mocked providers and generated-circuit simulator tests.

Role deployment and report actions stop waiting for their SDK result ten minutes after the transaction identifier has been durably saved. This application deadline includes the remaining wallet submission wait and finality observation; it does not change the SDK provider's indefinite watch behavior. On expiry, the saved identifier remains available, backup/export and locking are enabled, and further transactions in that workspace session are disabled. The underlying SDK may still poll, finalize and update its own in-memory provider; late results do not write a receipt or deployment address into the expired workspace. Keep the backup and investigate the journal identifier before restoring a fresh session. For deployment, recover the observed contract address explicitly instead of deploying again. Expiry is not failure evidence or permission to retry. Browser suspension can delay the timer; closing the tab ends its remaining SDK activity.

For a restored vendor backup with no contract address, check its recorded constructor attempt in the journal. If the sources report a finalized SUCCESS containing exactly one deployment action, **Use observed address in reconnect form** fills the existing-address field. This is a candidate from the indexer, not an authenticated program binding. The click does not connect Lace, save the address or change the backup. **Connect Lace and verify program** must still validate the saved program ID and vendor authority before updating the workspace; a failed check leaves the backup unbound. The shortcut is unavailable in an expired session, for unknown/non-constructor intent, or in the wallet-free inspector.

New report submissions retain a private snapshot of the current working notes and selected tier with their transaction identifier in role-vault v8 or later. Open **Private notes saved with this attempt** in the unlocked workspace's submission journal to read it. Editing today's notes does not replace that snapshot; encrypted file/browser recovery preserves both. Older attempts explicitly have no recorded private notes. This records working context, which may not be consumed by that circuit; it does not prove submitted arguments, broadcast or finality. The wallet-free journal inspector omits these private notes. See [ADR-0020](adr/0020-private-submission-notes.md).

Role-vault v9 introduced storage for the explicit **Pass retest** or **Fail retest** choice before the encrypted submission checkpoint completes. The unlocked journal displays it as local intent, not verified outcome. Old attempts remain unknown; later note/attachment edits and receipts preserve the choice. Versions 1–8 still restore, but older releases cannot read v9 backups, so retain a compatible release when rolling back. The wallet-free inspector also omits this private choice. Report reconciliation compares that choice and the exact saved notes with the replayed retest commitment. For v9 entries the patch was not independently saved, so their comparison remains partial. Missing older choices remain explicitly unverified.

If Lace or workspace recovery is unavailable, use **Inspect recovery journal without a wallet** below the role-restoration form. Select a downloaded role backup or load/select a browser copy, enter its password and choose **Read recovery journal**. Decryption and journal inspection make no network requests and install no role session. The screen shows backup network/contract claims and transaction identifiers; it does not verify authority or display actor secrets or report contents. Choose a status or report-effects check only when you want to contact the configured public services. **Clear inspected journal** removes the displayed projection and password and cancels pending checks. The encrypted source remains selected; JavaScript cannot guarantee forensic erasure of transient decrypted memory. An old backup with no entries is not evidence that no transaction was sent.

For an entry with saved report-operation intent, open **Reconcile this report operation** and choose **Check report effects**. This downloads public historical evidence and runs the transaction in a background worker, checking the saved program and report identities. It can take up to 90 seconds; **Cancel report check** stops it. A successful result shows the replayed before/after report status. It does not validate every intended argument, authenticate proofs or deployed code, transfer funds, or establish that retry is safe. Legacy entries without report intent and deployment entries do not offer this check. Results are not persisted in the backup. See [the evidence and limitations](transaction-content-investigation.md#browser-recovery-journal-check).

Pending fields under **Enter an existing digest** are included in role-vault v7 backups and browser autosave, even before they form valid attachment metadata. Wait for the saved confirmation before closing. After restoring, reopen that section to finish the filename, media type, byte size and SHA-256; choose **Add attachment metadata** or **Clear attachment fields** before sealing. Each pending field is limited to 4 KiB. Original file bytes and hashing progress are not backed up. See [ADR-0019](adr/0019-pending-attachment-drafts.md).

New retest attempts now use v10 and retain the patch commitment from the actual command along with Pass/Fail and note snapshots before encrypted persistence completes. Reconciliation checks this saved patch against the replayed patch and uses the saved value to calculate the expected retest commitment. Later edits cannot replace it. Versions 1?9 still restore with unknown patches preserved; older releases cannot open v10 backups. Keep a compatible release available for recovery and rollback.
